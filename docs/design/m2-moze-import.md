# M2 MOZE 匯入設計

M2（issue #5）把一份 MOZE 匯出的 CSV 匯進帳本。用語以 `CONTEXT.md` 為準，分層與依賴以 `docs/architecture-conventions.md` 為準，帳本的規則以 `docs/design/m1-ledger.md` 為準。本檔記錄 M2 的設計決定；實作與本檔不一致之處以程式碼為準，並回頭修正本檔。

## 1. 原則

- **匯入只經帳本自己的 use case。** 它是新的 context `importer`，只 import `finance` 與 `catalog` 的 `usecase/port/in`（`.golangci.yml` 的 `importer-*` 規則與既有的 `finance-boundary`、`catalog-boundary` 檢查）。沒有資料表、沒有 migration、沒有直接寫表的路：匯入記下的每一筆，帳本對任何呼叫者都一樣檢查。
- **匯進去的一律是草稿**，不影響餘額、預算與報表，使用者看過之後**逐月確認**。不存在繞過草稿的路。
- **使用者先看過每一個猜測。** 帳戶與標的建好之後不能再改，所以對照檔裡還有標了 `# guessed` 的項目時，`apply` 不執行。
- **匯入沒有網路、沒有背景工作。** 本位幣金額取自使用者自己備好的匯率檔（第 8 節）。
- **可重複，而且改了的東西到得了帳本。** 同一份檔案跑第二次什麼都不改，更長的新匯出只加新的列；對照檔、列的覆寫或匯率檔改了之後再 `apply`，草稿跟著改，已確認的則報出來（第 4 節）。
- **不默默丟東西。** 記不進帳本的列、記下來卻與 CSV 金額不同的單位、沒有地方放的文字，都列在 `plan` 的報告裡，有原因、對帳戶餘額的影響與建議的處理（第 5、6 節）。

## 2. 指令

`maxos import moze <指令>`。五個指令都有 `--file`、`--mapping`、`--rates` 三個旗標；沒給的取自 `MAXOS_MOZE_DIR`（`pkg/config` 讀，列在 `.env.example`，預設 `~/.config/maxos/moze`）：匯出是其中最新的 `MOZE_*.csv`，對照檔是 `mapping.yaml`，匯率檔是 `rates.csv`。輸出一律是繁體中文，金額照標的的小數位數；只有帳本拒收一個單位或一筆對帳的原因，照帳本的錯誤訊息（英文）原樣顯示。

| 指令 | 做什麼 | 寫資料庫 |
|---|---|---|
| `plan [--out report.md]` | 讀匯出、對照檔、匯率檔，算出匯進去會變成什麼；把對照檔缺的項目加進去（標 `# guessed`）；寫出報告。沒有 `--out` 時報告印在標準輸出，有的話只印摘要。對照檔裡還有猜測時照樣可以做 | 不連資料庫 |
| `apply` | 對照檔有缺項、有問題，或還有任何標了 `# guessed` 的項目時拒絕（說缺什麼、還有幾個猜測，叫人先 `plan`、看過、把標記拿掉）。否則冪等地建立參考資料（標的、機構、帳戶、類別、領域、專案、標籤、對象），再把每個單位記成草稿：帳本已有、內容一樣的不動（「已存在」）；帳本有的草稿與現在的對照不同，捨棄重記（「已更新」）；已確認的與現在的對照不同，不動、不在旁邊再記，報出來（「已確認的內容與對照不同」）並以非零狀態結束。帳本拒收的單位列出來、不擋其他；再跑一次報「新增 0 筆，已更新 0 筆」 | 只經 use case |
| `confirm --month YYYY-MM` | 依日期確認該月匯入的草稿，對帳該月的 MOZE 餘額調整；更早的月份還有沒確認的、或該月（含更早）有已確認但與對照不同的單位就拒絕；結束時印出該月底每個帳戶與標的的帳本餘額對照 CSV 的預期餘額 | 只經 use case |
| `verify` | 對每個已確認的月份做同樣的比對；有無法解釋的差異、或有已確認但與對照不同的單位，就以非零狀態結束 | 只讀 |
| `status` | 每月的草稿、已確認、略過的列、待對帳、尚未匯入、已作廢，與已確認但與對照不同的單位數 | 只讀 |

## 3. 檔案

匯出的 CSV 與 `mapping.yaml`、`rates.csv` 都是使用者的個人資料，不進版控；測試用的檔案都是為測試寫的假資料。

### 3.1 匯出

UTF-8，常有位元組順序記號，16 欄：`帳戶, 幣種, 記錄類型, 主類別, 子類別, 金額, 手續費, 折扣, 名稱, 商家, 日期, 時間, 專案, 描述, 標籤, 對象`。欄位以名稱找，不依順序；有引號、逗號與多行的「描述」；「初始金額」沒有日期與時間，其餘的列一定有日期。金額帶正負號（錢出去的為負），手續費為零或負，折扣為零或正。日期是 `YYYY/MM/DD`，時間是 `HH:MM`，檔案由舊到新。格式讀不了的列（欄位數不對、金額不是數字、沒有日期）是錯誤，指出行號；不認得的 MOZE 記錄類型不是錯誤，會列在報告裡。

### 3.2 `mapping.yaml`

使用者看過、保管的對照檔。`plan` 只**加**它缺的項目，每一項寫成一行並標 `# guessed`，其餘（註解、順序、引號、換行風格）原封不動；加的時候先確認寫出來的檔案讀回來，每一項的值都和原來一樣（加的項目是要的），不然拒絕、檔案不動。看過、改好的項目把標記拿掉。未知的鍵是錯誤。

```yaml
instruments:        # 依幣別代碼；TWD 是本位幣，不用寫
  USD: {name: 美元, kind: fiat, is_currency: true, decimals: 2}
  USDT: {name: Tether USDT, kind: crypto, is_currency: true, decimals: 2, rate_as: USD}
  BTC: {name: BTC, kind: crypto, is_currency: false, decimals: 8}
accounts:           # 依 MOZE 的帳戶名稱；幾個 MOZE 帳戶可以是同一個帳本帳戶
  "示範 Cube 卡": {name: 示範 Cube 卡, kind: card, institution: 示範, closing_day: 5, payment_due_day: 20}
  示範銀行 活存: {name: 示範銀行, kind: bank, institution: 示範, opening_date: 2025-01-07}   # 期初餘額的日期，不寫就是該帳戶最早一列的前一天
projects:           # 依「專案」欄的值
  日常: {kind: area, name: 日常}
  示範之旅: {kind: project, name: 示範之旅, default_area: 玩樂}
  募資商品: {kind: tag, name: 募資商品}
  公司代付: {kind: dealings, party: 公司}
  旅遊: {kind: none}
categories:
  expense:          # 依「主類別/子類別」；字串是帳本的類別路徑（「父」或「父/子」）
    "飲食/午餐": 飲食/午餐
  income:
    "收入/收款": {category: 收款（待確認）, tag: 待確認}
    "收入/信用卡抵扣": {treatment: reward}
    "收入/公司代收款": {treatment: dealing, party: 公司}
parties: {小明: 小明}   # MOZE 的名稱 → 帳本的名稱
tags: {家庭: 家庭}     # 標籤，不含 #
defaults: {fee_category: 手續費, interest_category: 利息支出, refund_category: 退款}
rows:               # 依列的 key（第 4 節）；改單一列的處理方式
  "9f2c…-1": {treatment: dealing, party: 小明}  # income | expense | reward | dealing | skip
  "9f2c…-2": {quantity: "0.0123"}                # 數量匯出為 0 的買賣：填了就記成買賣
```

猜測的規則（都標 `# guessed`）：

- **帳戶**：種類由名稱裡的字推（信用卡、銀行、證券、現金、錢包、wallet…）；名稱沒說是什麼、又只持有加密貨幣的是交易所。機構取名稱開頭到「卡／銀行／空白」之前；幾個帳戶的名稱開頭同樣兩個中文字，就是同一個機構。帳戶名稱照 MOZE 的，不猜合併：一個帳本帳戶可以持有幾種標的，要把幾個 MOZE 帳戶（例如同一家銀行的台幣與外幣帳戶）併成一個，就把它們的 `name` 改成一樣，種類與機構要一致。唯一的例外是帳單分期的列分在兩個 MOZE 帳戶時，猜成同一個帳戶（第 5 節）。
- **標的**：USD、JPY 等是外幣，USDT、USDC 是 `is_currency` 的加密貨幣且取 USD 的匯率（`rate_as`），其他是非幣別的加密貨幣，8 位小數。
- **專案欄**：「…代付」是往來；名稱像日期開頭、之旅、專案的是專案，其餘是領域；數量不多的已知詞（募資商品）是標籤。專案名稱去掉日期、符號與「專案」二字。預設領域只在對照檔裡真有那個領域時猜。
- **專案的進行期間，匯入從不設定。** 帳本把日期落在進行期間、又沒有專案的交易自動歸入該專案（M1a 的規則），匯入關不掉這件事。先前依列的日期猜出來的進行期間，在真實匯出上把 62 筆沒有專案的交易歸進了旅行專案，所以現在建專案只帶預設領域；`plan` 的報告在每一次都列出每個專案值的列數與日期範圍，專案另附「列的日期看起來是哪一段」，僅供參考（規則：至少 80% 的列落在一段連續的日子裡、且不只一天；預訂得早的列不拉長它，分散的列不猜）。要設定進行期間，使用者到帳本裡設，再依需要重新匯入。對照檔裡不再有 `active_period` 這個鍵，寫了是錯誤。
- **類別**：支出「主/子」照樣建兩層（兩者同字就一層）；收入的主類別只是「收入」時只取子類別。

## 4. 辨識與可重複

**列的 key。** `AssignKeys`：對列的正規化內容（每欄去頭尾空白、金額與日期用標準寫法，所以位數與格式的差異不影響）取 SHA-256 的前 24 個十六進位字元，後面接「同樣內容的列在檔案中的第幾個」（從 1）：`<hash>-<n>`。新匯出只在後面多了列時，原有的列 key 不變；完全相同的兩列各有自己的 key。MOZE 裡改了一列的內容，它就是另一列：舊的草稿還在，成為「孤兒」（`status` 與 `confirm` 會說有幾筆，不動它）。

**單位的 ID 與版本。** 一個單位（一筆交易、兩筆、或一個分期計畫）由它的列辨認：**ID** 是一列的單位的列 key；轉帳、換匯、買賣兩列，`<轉出的 key>+<轉入的 key>`；分期計畫是 `plan-<第一列的 key>`。**版本**是單位對帳本說的一切的指紋（`Unit.Fingerprint`）：種類、日期與時間、文字、領域、專案、標籤、各腿與各行的帳戶、標的、金額、類別、折扣、備註、手續費、各期、對象。標籤的次序不算；數字的寫法不算。

**冪等鍵。** `moze:<ID>@<版本>`；全額折扣的第二筆（回饋）是 `…#reward`；餘額調整的對帳是它那一列的 `moze:<列 key>`（沒有版本）。長度在帳本允許的 8 到 128 字元內。分期各期的鍵由帳本自己從起點推出（`instalment:…`）。

版本在鍵裡，是因為帳本對看過的冪等鍵一律回傳它存的那一筆，不管這次要的是什麼：鍵只由列組成的話，對照檔、列的覆寫或匯率改了之後，帳本仍說「已經記了」，確認的還是舊草稿，`verify` 也看不出來。有了版本，現在的對照與當初記下的是兩把不同的鍵，差異看得見（規格寫的是 `moze:<key>`，這是與規格不同的一點，見第 9 節）。

**改了的東西怎麼到帳本。** `apply` 先讀帳本裡匯入記下的交易（以前綴 `moze:` 辨認），對每個單位：

| 帳本有的 | 做什麼 |
|---|---|
| 這個 ID 的現在這一版，齊全 | 不動，「已存在」，也不呼叫帳本 |
| 現在這一版只有一部分（全額折扣的支出記了一半） | 補上缺的，算「新增」 |
| 這個 ID 的別的版本、或用到這個單位的列的別的 ID（轉出與轉入換了配法），全是草稿或已作廢 | 捨棄草稿，記現在這一版，「已更新」 |
| 其中有已確認的 | 不動它，也不記現在這一版（兩筆都確認之後這個單位就記了兩次）；報「已確認的內容與對照不同」。`apply`、`confirm`、`verify` 都以非零狀態結束，直到使用者把它作廢，下一次 `apply` 就會記成草稿 |

已作廢的現在這一版是使用者對這一版的決定，保持作廢；對照改了之後，新的一版會記成草稿。同一分鐘的轉出與轉入依檔案次序配，所以列的次序變了、或插了新的列而配法變了，舊的配法與新的配法用到同樣的列，上面的規則就擋住第二筆轉帳。

**怎麼分辨自己的交易。** 以冪等鍵的前綴 `moze:`。這是帳本現有的東西：不需要新欄位、新標籤或收件連結，`ListTransactions` 回傳的每筆交易帶著鍵。`confirm` 只確認 plan 認得的鍵（所以不會動使用者在別處記的草稿）；分期計畫的各期不是 `moze:`，它們跟著起點確認。

**巢狀交易（savepoint）。** 匯入不用：每個 use case 呼叫都是自己的、最外層的資料庫交易，匯入的 use case 不開交易（它們也不能 import `pkg/`）。一次 `apply` 不是一個交易：失敗了就是少了幾個單位，再跑會補上，草稿本來就不影響任何數字。`pkg/postgres` 的 `withinSavepoint` 因此只剩它自己的測試在用。

## 5. 處理方式

匯入把 MOZE 的列變成「單位」，每個單位用帳本的一個 use case 記下。下表用 MOZE 的記錄類型稱呼列，用帳本的種類稱呼記下來的交易。

| MOZE | 帳本 |
|---|---|
| 支出 | `RecordExpense`，一個類別行；實付 = 金額 + 折扣（金額為負，折扣為正），折扣記在行的 `Discount`；手續費欄是另一個類別行（手續費類別）。折扣等於或大於金額（點數付全額）：全額的支出，加上同一帳戶、折扣金額的一筆 `RecordReward`，兩筆交易（折扣大於金額的列另外提醒）。帳戶最後的變化永遠是 金額 + 折扣 + 手續費，與 CSV 一致 |
| 支出，專案是「…代付」 | 不是支出：`RecordDealing` 付出給那個對象，金額是實付，折扣在描述裡寫明（往來沒有折扣欄）。**手續費記成往來的手續費**，也就是使用者自己付的手續費支出（第 9 節） |
| 收入 | `RecordIncome`，手續費記成它的手續費；子類別「信用卡抵扣」是 `RecordReward`；「公司代收款」是 `RecordDealing` 收回；其餘照類別對照 |
| 收入「收款」（來源不明） | 預設記成類別「收款（待確認）」的收入、貼標籤「待確認」，報告逐列列出 key；每一列可在 `rows` 改成往來（`dealing`）、別的類別（`income`）、回饋、或略過 |
| 紅利回饋 | `RecordReward`，手續費記成它的手續費 |
| 應收款項 | `RecordDealing`，對象取「對象」欄，金額為負是付出（對方欠我更多）、為正是收回；手續費記成往來的手續費 |
| 退款 | 帳本沒有退款這個種類：記成類別「退款」的收入，原本的類別留在備註，手續費記成收入的手續費 |
| 手續費（類型）、利息 | 手續費類別、利息類別的支出（沒有被分期計畫收進去的利息）；手續費欄另成一個手續費類別行 |
| 轉出 ＋ 轉入 | 見下：同標的是 `RecordTransfer`，兩種幣別是 `RecordExchange`，一邊是非幣別且數量不是 0 是 `RecordTrade`；兩邊的手續費各記一筆 |
| 初始金額 | `SetOpeningBalance`，日期是該 MOZE 帳戶（與標的）最早一列的前一天；對照檔的帳戶有 `opening_date` 就用它。沒有任何有日期的列時取同一個帳本帳戶、再不行取整個檔案最早一列的前一天（報告提醒）。金額為 0 的不記，因為帳本不收。更長的匯出多了更早的列時，期初餘額的日期跟著往前，帳本裡的草稿因此更新；要讓它留在原處，就在對照檔指定 `opening_date` |
| 餘額調整 | `apply` 不記；`confirm` 時才對帳（第 7 節），對帳交易的描述是「對帳（MOZE 的餘額調整）」，接著名稱與描述，商家、專案、標籤也留著。調整金額是這一列對帳戶的影響（金額加折扣加手續費）。影響為 0 的不存任何東西 |
| 帳單分期、分期還款、利息 | 一組 `帳單分期`（MOZE 在同一分鐘寫下的幾列，淨額為正）加上它之後的 `分期還款`，本金依序加起來剛好等於淨額，就是一個 `RecordBillInstalment`：本金、扣款日取自各筆分期還款，利息取同帳戶同一天的 `利息` 列，帳單分期各列的手續費記成這個分期的手續費。各列要對到同一個帳本帳戶，否則整組不記並指出該把哪些帳戶合併（猜測會先幫你合併）。湊不起來的，利息照上面記成支出，其餘列出 |
| 文字 | 名稱、商家、時間、描述、專案、標籤都留著，沒有哪一欄被丟掉：名稱是描述，商家是商家，時間是 `OccurredAt`（使用者時區），專案與標籤是領域、專案、標籤；描述在支出與收入裡是類別行的備註（發票明細），在沒有類別行的交易裡接在描述後面，沒有地方放的欄位（例如轉帳兩邊各有不同的商家、被收進分期計畫的利息列的名稱與描述）以帶標籤的一行接在描述後面。沒有類別行的交易（往來、轉帳…）把原本的「主/子類別」附在描述最後，如「〔應收款項/借出〕」。帳本的文字欄位沒有長度上限，沒有東西被截掉 |
| 專案、領域、標籤 | 對照檔決定；有專案沒有領域時，帳本自己帶專案的預設領域 |

**轉出與轉入怎麼配。** 同一天同一分鐘的轉出與轉入是一對。同一分鐘有好幾筆時，依金額配：同標的的兩邊要金額相同，不同標的的兩邊不論金額都可以配。只有一種配法，或者所有配法得到的轉帳都一樣（相同的列依檔案順序配），才採用；有不只一種配法、一種都配不出，或者兩邊筆數不等，整組不匯入，列在配對問題裡。同標的、金額不同、同一個帳戶（合併之後）、兩邊都不是幣別的，也不匯入。手續費記在它所在的那一列的帳戶與標的；兩邊都有就是兩筆手續費。子類別是「兌換」但兩邊同標的（換匯需要兩種幣別）記成轉帳，並提醒。

## 6. 記不進帳本的，與提醒

下面的列都在報告裡，每組有原因、對帳戶餘額的影響（帳本會比 CSV 少掉這些）與建議的處理；`confirm`、`verify` 把這個影響當成**已說明的差異**，其餘的差異才讓 `verify` 失敗。

| 原因 | 處理 |
|---|---|
| 買賣的非幣別標的（加密貨幣）匯出的數量是 0 | 沒有數量就不能記成買賣，預設不匯入：付款帳戶的餘額會比 CSV 多出付出的金額。查到數量後在 `rows` 填 `quantity`，就記成買入或賣出，那一列的預期餘額也照這個數量算 |
| 轉出或轉入沒有另一半、配對有歧義、金額對不上、兩邊同帳戶、兩邊都不是幣別 | 預設不匯入，報告列出 |
| 帳單分期的列湊不成計畫，或各列在不同帳戶 | 預設不匯入 |
| 金額的正負號不對、金額為 0、小數位數超過標的 | 不匯入 |
| 沒有類別的支出或收入、沒有對象的往來增減、整份檔案沒有任何日期可以放初始金額 | 不匯入（對照檔補上類別或對象就會記） |
| MOZE 的記錄類型不認得 | 不匯入 |
| 對照檔指定 `skip` | 照辦 |

**記下來、但金額與 CSV 不同的單位。** 帳本在某些單位上沒有地方記某些欄：只有支出有折扣，分期還款的列沒有手續費的位置。每一個單位記下來之後會影響哪些帳戶，與它的列在 CSV 裡的影響，`plan` 逐一比對；不同的列在報告的「記下來、但金額與 CSV 不同的單位」一節，有原因（手續費、折扣、原因不明）與帳本少記的金額，這個差額也算進已說明的差異。所以 `plan` 沒有列任何這種單位、也沒有無法記錄的列時，`confirm` 與 `verify` 不會有無法解釋的差異。

**有記錄、但要知道的**：

- **投資**（類別「投資」的支出與收入）與**證券戶**（種類 `brokerage`）：匯出沒有數量，不能記成買賣，所以照原本的類型記成支出、收入、轉帳；帳戶餘額與 CSV 一致，持有的標的不會在淨資產裡。證券戶以台幣市值記，沒有數量；有數量之後（M5）可改記成買賣。
- 折扣大於金額、同標的的兌換、退款、待確認的收款、期初餘額日期的退而求其次：各一節，列出每一列。

## 7. 確認程序

`confirm --month YYYY-MM`：

1. 該月之前任何一個月還有匯入的草稿沒確認、有單位沒有 `apply`、或有對帳沒做完，就拒絕，指出是哪個月。該月自己有沒 `apply` 的單位也拒絕。對照檔有缺項或有問題時拒絕。該月與更早的月份有已確認、但與現在的對照不同的單位時也拒絕（「已確認的內容與對照不同」）：把它們作廢，再 `apply`。
2. 逐日（日期由舊到新）：先確認那天的草稿（一次 `ConfirmTransactions`，全有或全無，依 plan 的順序），再做那天的對帳。
3. **對帳** = MOZE 在某個日子把帳戶補成實際餘額（MOZE 的餘額調整）。對每一筆（非零的）：到那一天為止這個帳戶與標的的所有草稿都確認了，就以 `GetBalances` 讀帳本到那天的餘額，呼叫 `Reconcile`，實際餘額 = 該餘額 + 調整金額；幣別的差額記成「未記錄」（外幣帶用匯率檔算的本位幣金額），非幣別標的只改數量；再確認那筆對帳。帳本在有別人的草稿（日期在那天或之前、動到同一個帳戶與標的）時拒絕對帳（`*PendingDraftsError`）；匯入把它當成這筆對帳被擋下，說出原因，繼續做別的，最後以非零狀態結束。對帳以日為單位：同一天的對帳在那天所有交易之後，所以每一次對帳的「實際」都是 CSV 那個時刻之後、同一天全部確認完的餘額加上調整，月底的結果與 CSV 一致。已經做過的對帳（鍵已用過）不會再做。
4. 結束時印出該月底每個帳戶與標的的帳本餘額，與 CSV 算出的預期餘額（含 MOZE 的餘額調整、期初餘額從它的日期起算）。差額 = 帳本 − 預期；其中因為不匯入的列、與記下來但金額不同的單位造成的部分是已說明的，其餘的是無法解釋的，指出來並以非零狀態結束。
5. 別人的草稿（鍵沒有 `moze:` 前綴，或不在 plan 裡）一律不動；匯入的草稿若已不在新的檔案裡（孤兒）也不動，只報有幾筆。

`verify` 對已確認的月份（從第一個月起，連續到第一個還沒確認完的月份之前，那個月有草稿、尚未匯入的單位，或已確認但與對照不同的單位）做第 4 點的比對。分期計畫的各期隨起點在起點的月份確認，日期在後面的月份：餘額一向以日期算，所以月底的比對不受影響。

## 8. 近似與缺漏

- **本位幣金額是近似值。** 帳本要求外幣的支出、收入、回饋、手續費與利息有交易當天的本位幣金額（TWD）；匯出沒有，匯入從 `rates.csv` 取：金額 × 當天的匯率，四捨五入到小數兩位；沒有當天的匯率就用最近的較早的一天；沒有任何較早的匯率就是錯誤，不匯入（報告與 `apply` 都擋）。USDT 用 USD 的匯率。寫入之後這個金額不再變動，所以它只是「大約值多少」，不是銀行實際扣的。匯率檔改了、某個外幣單位的本位幣金額變了，那個單位就是另一版（第 4 節）：草稿會重記，已確認的會被報成與對照不同。
- **加密貨幣的數量**：匯出對非幣別的標的有不少列的數量是 0（見第 6 節）。
- **證券戶、投資**：沒有數量、沒有成本，不是買賣（見第 6 節）。
- **時間**：MOZE 常用 23:59 當沒有時間；照樣記成 `OccurredAt`。

### 匯率檔

`rates.csv`：`date,instrument,twd_per_unit`（一個標的一日一行，每一個單位換多少 TWD），`#` 開頭是註解。`TWD` 不寫；USDT 不寫（取 USD）。

來源與類型：美國聯邦準備理事會 H.10 的每日匯率（紐約中午的買入匯率，銀行間匯率，不是銀行的牌價也不是信用卡實際扣的），經 FRED 公開下載：`DEXTAUS`（每美元換多少 TWD）、`DEXJPUS`（每美元換多少 JPY）；USD = `DEXTAUS`，JPY = `DEXTAUS ÷ DEXJPUS`。假日沒有資料，那天用最近的較早一天。這是一次性的取得指令，匯入本身不連網路；匯出更新到更晚的日期時，重跑一次：

```bash
#!/usr/bin/env bash
# 用法：build-rates.sh 起日 迄日 > rates.csv，例如 build-rates.sh 2024-12-01 2026-11-30
set -euo pipefail
from=${1:?起日 YYYY-MM-DD}
to=${2:?迄日 YYYY-MM-DD}
fred() { curl -fsS "https://fred.stlouisfed.org/graph/fredgraph.csv?id=$1&cosd=$from&coed=$to"; }
echo "# Daily rates for maxos import moze: TWD per one unit of the instrument."
echo "# Source: Federal Reserve H.10 noon buying rates in New York (interbank), via FRED: DEXTAUS (TWD per USD), DEXJPUS (JPY per USD)."
echo "# USD = DEXTAUS; JPY = DEXTAUS / DEXJPUS. USDT takes the USD rate (rate_as in the mapping). Holidays have no row: a day takes the nearest earlier one."
echo "# These are approximations of what the money was worth, not what the bank charged. Built $(date +%F) with the command in docs/design/m2-moze-import.md."
echo "date,instrument,twd_per_unit"
awk -F, -v OFS=, '
  FNR == 1 { file++; next }
  $2 == "" || $2 == "." { next }
  file == 1 { twd[$1] = $2; order[++n] = $1; next }
  { jpy[$1] = $2 }
  END {
    for (i = 1; i <= n; i++) {
      d = order[i]
      print d, "USD", twd[d]
      if (d in jpy) printf "%s,JPY,%.6f\n", d, twd[d] / jpy[d]
    }
  }' <(fred DEXTAUS) <(fred DEXJPUS)
```

## 9. 與規格不同

下面是與 `local://m2-import-spec.md`（M2 的規格）不同、或規格沒有說而這裡決定了的地方，請使用者看過、決定：

1. **冪等鍵含版本**（規格：`moze:<key>`，轉帳由兩列導出）。沒有版本，改了對照之後的 `apply` 到不了帳本（第 4 節）。
2. **同標的的「兌換」記成轉帳**（規格：子類別「兌換」→ `RecordExchange`）。帳本的換匯要兩種不同的幣別（`app/finance/domain/model/errors.go` 的 `ErrSameInstrument`），同標的的兌換記不成換匯；報告逐列提醒。
3. **時間記成 `OccurredAt`**，不是文字欄位（規格：時間留在交易既有的文字欄位）。帳本有真正的時間欄位，用它。
4. **公司代付的支出若有手續費，那筆手續費是使用者自己的手續費支出。** 公司代付的支出是對公司的往來付出，不是支出；MOZE 的手續費欄記在同一列，匯入把它記成往來的手續費（帳戶付出金額加手續費，手續費記在手續費類別）。規格沒有說這筆手續費算誰的；若它其實是公司該出的，改這些列的處理（`rows`）。
5. **帳戶 38 → 37 個**：帳單分期的偽帳戶併進信用卡（猜測做，使用者可改）。
6. **「identified repayments」不會自動辨識**：規格說公司代收款與已辨識的還款記成往來收回；匯入只認 `公司代收款` 這類類別與使用者在 `rows` 或對照檔指定的，其餘照原本的類別記。
7. **專案的進行期間不設定**（規格：日期明顯時，專案帶進行期間）。理由見第 3.2 節。
8. **匯入名稱**：對帳（Reconciliation）的交易描述寫「對帳（MOZE 的餘額調整）」；「餘額調整」是 MOZE 的說法，不是本專案的用語。

## 11. 測試

沒有真實資料：測試用的 CSV 與對照都是為測試寫的假資料。

- 解析（`adapter/out/file`）：引號、多行描述、BOM、初始金額沒有日期、正負號、小數、欄位順序、行號、key 的穩定性。
- 對照檔：載入、錯誤（含 `active_period` 不再是鍵）、加項目（保留原檔一字不差、不重複加、新檔來回、`opening_date`）、加完讀回來每一項的值要和原來一樣（區塊字串裡長得像註解的行不會讓新項目插進別的項目的值裡）。
- 規則（`domain/service`）：每種處理方式、每個「不能記」的分支、配對（相同的列、金額配、歧義、缺一半、跨幣別、手續費在哪一邊）、分期（對得上、帳戶不同、對不上）、猜測、預期餘額、手續費與折扣在每種單位上的去處與帳本記不下的差額、文字一欄都沒有被丟掉、期初餘額的日期、報告裡沒有英文句子。
- use case（`usecase/moze`，帳本是記憶體裡的假實作，它依輸入算出對各帳戶的影響）：每種單位呼叫的 use case 與輸入、`apply` 兩次一樣、更長的檔案只加新的列、帳本拒收的、**對照或列的覆寫改了之後的 `apply`**（草稿更新、已確認的報出、作廢後重記）、同一分鐘的轉帳換了配法不會記兩次、中斷的 `apply` 接著做、專案沒有進行期間、猜測沒拿掉標記時 `apply` 拒絕、月序、對帳的時機（同一天前後都有交易）、別人的草稿不動、每個月底的帳本餘額等於 CSV 預期扣掉不匯入的、`verify`。
- `cmd/` 的端到端（真的 PostgreSQL、假檔案、真的 Cobra 指令）：`plan` → `apply` 因為猜測拒絕 → 看過 → `apply` ×2 → 專案與領域 → 覆寫一列再 `apply`（草稿更新）→ `confirm`（順序、兩個月）→ `verify` 回傳成功；一筆已確認的交易與對照不同時 `apply`、`confirm`、`verify` 失敗，作廢之後 `apply` 重記、`confirm` 與 `verify` 回傳成功；再多一筆不是匯入的已確認交易，`verify` 失敗。
