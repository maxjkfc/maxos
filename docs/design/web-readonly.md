# 唯讀網頁設計

`maxos serve` 在 `/app/` 底下提供一組唯讀的網頁，看帳本裡的資料與圖表。用語以 `CONTEXT.md` 為準，分層與依賴以 `docs/architecture-conventions.md`（尤其第 11 節）為準。本檔記錄這組網頁的決定；與程式碼不一致之處以程式碼為準，並回頭修正本檔。

## 1. 範圍

- 只讀。之後頁面要能做操作（確認、記帳……），所以結構上留好位置（第 5 節），但現在沒有任何寫入的路徑。
- 與 `/mcp` 同一個 Cloudflare Access：沒有未驗證的入口，沒有關掉驗證的開關。
- 聊天式的查詢（MCP 的查詢工具）留給 M3，網頁與它無關。
- 介面是繁體中文，詞彙照 `CONTEXT.md`（帳戶、餘額、交易、種類、草稿、類別、領域、專案、預算、分配、往來、對象、帳單、結帳日、繳款日、入帳日、未到期分期、未記錄……），不用它的 `_Avoid_` 欄列的詞：`glossary_test.go` 從 `CONTEXT.md` 讀出每個 `_Avoid_` 的詞（名字是別的詞條、或是種類的名字的除外），每個測試取得的每一頁都對照它，連 404 與 400 的頁面也是。

## 2. 路由

每條路由都在 Access verifier 後面；沒有 token 的請求得到和 `/mcp` 一樣的 `401 unauthorized`。

| 路徑 | 頁面 | 參數 | 呼叫的 use case（另外每頁讀一次需要的參考清單） |
|---|---|---|---|
| `/app/` | 總覽（首頁）：帳戶餘額（各標的的合計，有草稿等著確認時是預覽）、一排卡片（本月支出、等著確認的草稿、往來）、信用卡的繳款日（自成一張與頁面一樣寬的卡片）、兩張支出的圖、帳戶依種類的餘額、未到期分期 | | `GetPreviewBalances`、`GetDealings`、`ListInstalmentPlans`、`GetDraftSummary`、`GetSpending`、`GetSpendingTrend`、`ListCardStatements`（每張使用中、設了結帳日的卡一次） |
| `/app/transactions` | 一個月的交易，可篩帳戶、狀態、種類 | `month=YYYY-MM`、`account`（帳戶 id，或 `none`：沒有帳戶的交易）、`status`、`kind`、`periods`（只能是 `none`：分期計畫只列起點，不列各期）、`page` | `ListTransactions`（一頁 100 筆） |
| `/app/transactions/{id}` | 一筆交易的所有部分、標籤、所屬的分期計畫 | | `GetTransaction`、`GetInstalmentPlan`（屬於計畫時） |
| `/app/drafts` | 草稿依月份再依帳戶分組，附筆數與金額 | | `GetDraftSummary` |
| `/app/cards` | 信用卡：進行中的一期與最近結帳的十二期 | | `ListCardStatements`（每張設了結帳日的卡一次） |
| `/app/cards/{account}` | 一張帳單：數字、交易（舊的在前）、依類別的消費 | `closing=YYYY-MM-DD`（帳單裡的任何一天，預設今天） | `GetCardStatement` |
| `/app/budgets` | 領域與專案的預算、已花、分配、未分配 | `month=YYYY-MM` | `GetAreaBudgets`、`GetProjectBudgets` |
| `/app/spending` | 這個月依類別的支出，最近十二個月的支出合計 | `month=YYYY-MM` | `GetSpending`、`GetSpendingTrend` |
| `/app/static/app.css` | 唯一的樣式表 | | |
| `/app` | 轉到 `/app/`（驗證之後才轉） | | |

- `month` 不給就是今天所在的月（時區是 `MAXOS_TIMEZONE`，今天只來自時鐘 port）。查詢字串用 `url.ParseQuery` 讀：壞的跳脫、分號，與一頁收的參數給了不只一個值，都是 400 頁面；不合法的參數（不是月份、年份在 1900 到 2999 之外、不是 id、`page` 不是 1 到 10000）也是 400 頁面，說明是哪個參數該是什麼，不重複收到的值；不存在的 id、不是帳單的帳戶是 404 頁面；其他方法是 405；use case 失敗是 500 頁面，不說原因（記在日誌）。
- 一頁的 use case 呼叫數固定：列出來的東西一次取得，參考清單（帳戶、機構、標的、類別、領域、專案、對象、標籤）各讀一次，含已封存的，因為舊交易指著它們。隨數量增減的有兩處，都是每張信用卡一次 `ListCardStatements`（帳單的日子是各卡自己的，沒有一次給所有卡的讀取）：信用卡帳單總覽（每張設了結帳日的卡），與總覽的「信用卡」卡片（每張使用中、設了結帳日的卡，已封存的不問；只問今天前 35 天到後 31 天的幾期，就是最近結帳的一期與進行中的一期）。那是卡的張數，不是帳本的筆數：一個人有幾張卡，這一頁就多幾次，帳本再大也不多。總覽的呼叫因此是：六個 use case（`GetPreviewBalances`、`GetDealings`、`ListInstalmentPlans`、`GetDraftSummary`、`GetSpending`、`GetSpendingTrend`）、五個參考清單（標的、帳戶、機構、對象、類別）各一次，共 11 次，加上每張卡一次；`TestTheOverviewReadsInAFixedNumberOfCallsAndOneMoreForEachCardThatHasAClosingDay` 把這張表釘住。`GetPreviewBalances` 另外在 use case 裡讀帳戶與標的的清單，用來決定加總的種類與標的的順序，那是它自己的事，不是頁面的呼叫。`TestPagesIssueAFixedNumberOfCalls` 用一列與四百列的世界各讀每一頁，呼叫要完全一樣。
- 新增的讀取在 finance 的 `port/in`：`GetSpending`（頂層類別的合計）、`GetSpendingTrend`（「已花」與預算同一個定義，見 `m1-ledger.md` 第 5 節的「網頁用的讀取」）、`GetDraftSummary`、`GetPreviewBalances`（總覽的餘額：已確認的餘額加上草稿今天全部確認會有的變動，持有與未到期分期兩個數字，連同草稿的筆數與有沒有已確認的，一次讀取；取代總覽原本的 `GetBalances`，所以總覽的呼叫數不變。總覽改成首頁時多了 `Totals`（所有帳戶的餘額依標的加起來）與 `Kinds`（各種類的帳戶依標的加起來）：頁面不加總，大數字與各組的小計要有人加，就加在 use case，沒有新的 SQL，也沒有 migration，見第 4 節）、`GetCardStatement` 的 `Charges`、預算的每個分配的 `Over`，以及 `ListTransactions` 的 `Kind` 與 `WithoutAccount` 篩選。

## 3. 結構與安全

```
cmd/serve.go                      newHTTPHandler：安全標頭與 Access verifier 在最外面，裡面是 /mcp 與 /app/
cmd/web.go                        WebModule：各 context 的 registrar 收進 Fx 的 web.registrars；填 adapter 的 Ports 的 Fx struct 也在這裡
pkg/webserver                     Registry/Site：版面、導覽、錯誤頁、標頭、格式；不認識 context
pkg/svgchart                      圖表：資料進、SVG 出的純函式
app/finance/adapter/in/web        finance 的頁面：handler、view、templates/*.gohtml
internal/webtest                  測試用的 Access 替身（自簽金鑰）
```

- **守門**：`newHTTPHandler` 最外面是 `webserver.Secure(verifier.Middleware(mux))`，所以 mux 自己回的轉址與 404 也在驗證後面：沒有 token 的請求只得到 401，每個回應都帶標頭。`Registry.Pages(userOf, guard)` 的 guard 與 userOf 仍是必填，頁面自己也被它包住，所以頁面不靠被掛在哪裡；顯示的使用者是 token 的 email（服務 token 是 `service:<id>`）。只認 `Cf-Access-Jwt-Assertion` 標頭，不認 `CF_Authorization` cookie。沒有任何繞過驗證的開關；測試用 `internal/webtest` 的自簽金鑰，視覺檢查也是（第 7 節）。**`/mcp` 也帶這些標頭，而且 `Cache-Control` 是 `no-store, no-transform`**：go-sdk 在 `tools/call` 的 200 回應裡把它改成 `no-cache, no-transform`，蓋掉 `Secure` 設的 `no-store`，所以 `/mcp` 另外包一層 `webserver.NoStore`，在回應送出標頭的那一刻（`WriteHeader`、第一次 `Write`、`Flush`，或 handler 什麼都沒寫就返回）把它設回去；它實作 `Unwrap`，SDK 串流（SSE）的 flush 照常，其餘四個標頭不動。**`OPTIONS *` 也在驗證後面**：`net/http` 自己會在 handler 之前回它 200、沒有任何標頭，所以 server 設了 `DisableGeneralOptionsHandler`（`cmd.NewHTTPServer`，`serve` 與測試用同一個）：沒有 token 是 401 並帶標頭，有 token 是 mux 回的 400。被拒絕的請求記在日誌裡的路徑與原因最多 200 個字元（超過的接 `…`，另記原本的位元組數），客戶端給的 900 KB 路徑不會原樣寫進日誌。
- **標頭**（`webserver.Secure`，每個回應，包括 401）：`Content-Security-Policy: default-src 'self'; script-src 'none'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`（`/mcp` 是 `no-store, no-transform`）、`X-Frame-Options: DENY`。沒有 inline script 也沒有 inline style（進度條與圖表是 SVG 元素，以 class 上色），沒有 JavaScript、CDN、字型或圖片的外部請求。
- **方法**：只有 GET 與 HEAD，其他一律 `405` 並帶 `Allow: GET, HEAD`。
- **圖表**是伺服器產生的 inline SVG（`pkg/svgchart`：橫條圖、直條圖、進度條），所有文字都經過跳脫，連結只收站內路徑，幾何用 decimal 算，沒有浮點數。直條圖上高亮欄的數字畫在它蓋到的欄裡最高的那一根的上方，不壓在比它高的鄰欄上（數字的寬度由字數估計，估得寬一點；超出左右邊界時靠該欄的邊）。每張圖旁邊都有一張同樣數字的表，表是依據，圖是它的樣子；SVG 的 `<title>`/`<desc>` 也寫了同樣的數字給讀屏軟體。**總覽的兩張圖是例外**（版面小，卡片裡放不下兩張表）：十二個月的數字在柱狀圖下面折起來的表裡（`<details>`），類別的數字畫在橫條上，兩張也都寫在 `<desc>` 裡（第 4 節）。
- **可及性與版面**：真的 `<table>`、`<th scope>`、`<caption>`，數字靠右並用等寬數字，負數以負號（U+2212）標示，顏色只是第二個線索；超支同時有文字與顏色；亮色與暗色跟著系統（`prefers-color-scheme`），桌面寬度圖與表並排。手機寬度（40rem 以下）每一列排成一張小卡片，每格前面寫欄名（`data-label`；欄標題留給讀屏軟體，標記上的 `role` 讓它仍是一張表）；欄位多的表在手機與桌面之間保持寬度，在框內橫向捲動。交易頁的列表是例外，它有自己的排法，也是之後各頁要統一成的樣子（第 8 節）。
- **金額**依標的的小數位數、千分位；**日期**是帳本裡的日曆日（不轉時區），**時刻**（建立、確認、作廢、發生時間）以 `MAXOS_TIMEZONE` 顯示。

## 4. 各頁怎麼排、怎麼算

網頁只排版，數字是 use case 的（架構慣例第 11 節）。有取捨的地方：

- **總覽**（首頁）：由上而下是「帳戶餘額」（一個大數字）、一排卡片（本月支出、草稿等待確認、往來）、信用卡（自己一張卡片，與頁面一樣寬）、兩張支出的圖、帳戶依種類的餘額、未到期分期。每個數字都是 use case 的，頁面只寫（架構慣例第 11 節）；卡片與圖的版面規則在第 8 節。沒有「淨資產」的數字：它需要價格（M4、M5），所以大數字不換算、不加往來（第 6 節）。
  - **帳戶餘額**（大數字）：定義只有一個：**所有帳戶的預覽餘額的持有（沒有草稿時就是餘額），每個標的分開加起來**，是 `GetPreviewBalances` 的 `Totals`。包含下面帳戶區列出的每個帳戶，也包含已封存但還有餘額的帳戶，信用卡與貸款的負數照減；收進摺疊清單的零帳戶是零，不改變加總。不含：往來（對象欠的與欠對象的，是另一張卡片）、未到期分期（另列一行，在大數字下面，是欠機構的錢，負的）、任何換算（標的之間沒有匯率與價格）。大字是本位幣（TWD）的合計；其他標的各一個較小的數字排在下面，依代碼排序（use case 排的），每個帶自己的代碼，永遠不與別的標的相加。只有別的標的有餘額時，大字是 `0.00 TWD`（那是真的：本位幣沒有餘額），不拿別的標的頂替；一個標的的合計與已確認的部分都是零就不寫。合計的 `Basis` 是合計的已確認與草稿兩個和依同一條規則說的（見下），所以「已確認 x」「尚未確認」與紅色和帳戶的列同一個規則；兩個帳戶已確認的部分剛好互相抵銷時，合計沒有已確認的部分可寫，說「尚未確認」，各帳戶的列仍各說各的。
  - **預覽餘額**（總覽的帳戶餘額與各組帳戶，有草稿等著確認時；詞條在 `CONTEXT.md`）：帳本裡全是草稿時（匯入之後），已確認的餘額是空的，整頁看起來像沒有資料；預覽餘額讓人看到「如果草稿都確認了，各帳戶今天會有多少」，並標明那是預覽。數字是 `GetPreviewBalances` 的，頁面不加總、不判斷（架構慣例第 11 節）。定義只有一個，對每個帳戶、每個標的，`GetBalances` 的兩個數字（持有 ＝ `Quantity`，未到期分期 ＝ `UnbilledInstalment`）各一份：**預覽 ＝ 今天的已確認數字（`GetBalances` 今天的）＋ 所有草稿今天全部確認會有的變動**。變動是狀態為草稿、`occurred_on` 不晚於今天的交易的分錄加起來，各在自己的帳戶（分期計畫的各期在資料庫裡是各自的草稿，也算）：`account` 帳簿的分錄加進持有，`instalment` 帳簿的分錄加進未到期分期。持有的變動與草稿的合計同一條規則（`GetDraftSummary` 的金額，各帳戶所有月份的淨額加起來）：日期在今天之後的草稿與還沒到期的分期各期不算（到那一天才算），作廢的交易不算，沒有帳戶的草稿（對象先付的支出）不動任何帳戶；轉帳進出的兩個帳戶都算，各自的預覽都動，全部帳戶加起來不動（手續費除外）。未到期分期的變動是草稿計畫的本金：消費分期的起點讓那張卡欠整筆本金（未到期分期，持有不動），各期扣款日到了，那一期的本金從未到期分期移到持有，利息也進持有；帳單分期的起點把帳單還清（持有），同一筆轉成欠的本金（未到期分期），兩個數字的變動互相抵銷。只算持有的預覽會讓卡欠的比確認之後少：確認之後 `GetBalances` 的未到期分期才有這筆本金。四個測試把定義釘住（一條 SQL，`ListPreviewBalances`，與 `model.SummarizeDrafts` 是兩種寫法的同一個規則）：①確認全部草稿之後，每個帳戶每個標的的 `GetBalances` 兩個數字，就是確認前的預覽（含草稿的消費分期與帳單分期）；②每個帳戶持有的草稿部分，是 `GetDraftSummary` 各月份該帳戶的淨額加起來；③所有帳戶持有的草稿部分，每個標的加起來等於 `GetDraftSummary` 的總淨額（自己帳戶之間的轉帳淨額為 0）；④草稿的筆數就是 `GetDraftSummary` 的 `Count`。讀取是一份快照：餘額（一條語句）與筆數（`CountDrafts`，分期計畫算一筆）在 `WithinSnapshot` 裡讀，一筆草稿在讀的當中被確認，只會在已確認或草稿其中一邊，不會兩邊都有或都沒有。
  - **什麼時候是預覽**：`GetPreviewBalances` 的 `DraftCount` 不為 0；它與餘額是同一次讀取，所以標題、說明與每個數字說的是同一件事，頁面不自己數。它與草稿卡的筆數是同一個定義（分期計畫算一筆，日期在今天之後的也算，它們只是還沒影響數字）。「帳戶餘額」的標題旁是藥丸「預覽（含 N 筆草稿）」（N 有千分位），帳戶表的金額欄的欄名是「餘額（預覽）」；大數字下面的說明：各帳戶的餘額每個標的分開加起來、不換算，已確認的餘額加上這些草稿今天全部確認後會有的變動，草稿確認之後這裡會換成實際的餘額，並連到草稿頁。全都是草稿時（`HasConfirmed` 為假，匯入之後的樣子）改說「還沒有已確認的餘額，這些數字全是草稿」。沒有草稿時：標題只有「帳戶餘額」，欄名是「餘額」，沒有任何預覽的字，沒有「已確認」那一行。沒有任何帳戶有數字可寫時（有草稿等著確認、但都不動今天的餘額，或根本沒有），這張卡沒有大數字，只說「還沒有已確認的餘額。草稿確認之後，餘額會出現在這裡。」，有草稿時仍有藥丸。
  - **一個數字**：主數字是預覽。use case 給每個數字一個 `Basis`，頁面照它寫：`confirmed`（草稿沒動它）什麼也不加；`both`（有已確認的部分，草稿動了它）下面一行淡色小字「已確認 x」；`drafts`（沒有已確認的部分，整個是草稿的）下面一行「尚未確認」，不寫一排 0.00。已確認的數字是對照，不用紅色。**紅色只給有已確認基礎的負數**（`confirmed` 與 `both`，與沒有草稿時一樣）：整個是草稿的負數保留負號，用一般文字色，因為還沒有任何已確認的錢被花掉，整個帳本都是草稿時負數很多，標紅是一片假警報。這條規則對大數字、各組的小計與每一列都一樣，所以全是草稿時整頁沒有紅色。預覽的持有是零、而草稿抵銷了已確認的部分時（已確認 500、草稿 −500），仍列出一行「0.00　已確認 500.00」，不收進摺疊，也不被只剩下的未到期分期那一行取代；收進摺疊的「餘額皆為零的帳戶」的是預覽與已確認都是零的帳戶。
  - **與草稿卡**：草稿卡的「變動」（`GetDraftSummary` 的 `Amounts` 的 `Net`，每個標的一個，帶正負號）就是帳戶區每個持有數字的「預覽減已確認」依標的加起來（頁面的測試把頁面上的數字加起來驗證）。**未到期分期不在這個相等裡**：草稿的淨額只算 `account` 帳簿，分期計畫的本金不是帳戶的收支，它列在帳戶那一行「未到期分期」（那一行的草稿部分是 `instalment` 帳簿的分錄），所以草稿卡的說明這麼說，並寫明還沒到期的分期各期與日期在今天之後的草稿，要到那一天才影響餘額，預覽也不含。草稿的表（流出、流入、自己帳戶之間的轉帳）只在草稿頁。未到期分期的表（`ListInstalmentPlans`）只列已確認的計畫，預覽時表的說明加一句：還是草稿的計畫確認之後才列在這裡，它們還沒到期的本金已經算進帳戶的「未到期分期」。
  - **帳戶依種類**：一種帳戶一組，順序是銀行戶頭、信用卡、現金、投資帳戶、交易所、錢包、貸款（用字是 `CONTEXT.md` 的帳戶詞條與 `accountKindLabel` 的，「銀行」「證券」不是詞條），不認得的種類在最後，各依種類的名稱；組內照 `ListAccounts` 的順序（名稱）。一列是一個帳戶：名稱（連到它的交易頁；已封存的帶「已封存」）、機構（名稱下面一行淡色小字，現金與自己保管的錢包沒有機構，就不寫），右邊是各標的的數字（預覽、已確認、尚未確認、未到期分期，寫法與上面一樣）。組名旁寫這一組列出了幾個帳戶。**列出兩個以上帳戶的組，標題右邊寫它們的小計**：每個標的一個，是 `GetPreviewBalances` 的 `Kinds`（use case 把各種類的帳戶依標的加起來，依代碼排序），**絕不跨標的**，加起來是零的標的不寫；只有一個帳戶的組不寫小計（那就是它的列）。測試把頁面上的列加起來驗證：每一組的小計與大數字，等於列出來的帳戶的列依標的加起來。持有與未到期分期都是零、也沒有已確認的部分的帳戶，仍收進最後一個摺疊的清單（只列名稱），已封存又沒有餘額的不列。
  - **卡片**（一排，寬度夠就並排，最後一排的卡片撐滿那一排；標題右邊是去哪裡的連結）：
    - **本月支出**：`GetSpending` 今天所在的月，與預算的「已花」同一個定義（已確認、本位幣、算到今天為止）；下一行「上個月」取自 `GetSpendingTrend` 的倒數第二個月（不是零才寫）。這個月沒有已確認的支出時直說「這個月還沒有已確認的支出」，不寫 0.00；有草稿等著確認時指到草稿頁：草稿不算支出，這一步也不為草稿另讀一個「草稿的支出」。
    - **草稿等待確認**：`GetDraftSummary` 的 `Count`（有千分位）與 `Amounts` 的 `Net`：「全部確認後，帳戶的餘額今天會有這些變動」，每個標的一行，有正負號、不用紅色（那不是損失，什麼都還沒發生）；變動是零（日期在今天之後或沒有帳戶的草稿）時說「不會有變動」；沒有草稿時說「沒有等著確認的草稿」，沒有連結。
    - **往來**：只在有往來（任何一個對象的金額不是零）時出現，沒有就沒有這張卡。每個對象一列，每個標的一行，用字說出誰欠誰（正為「對方欠我」，負為「我欠對方」）；金額全為零的對象收進卡片裡摺疊的清單。
  - **信用卡**（不在上面那一排裡，自成一張與頁面一樣寬的卡片：卡有好幾張時，放在一排裡它會把整排撐得很高，旁邊的卡片空掉一大半）：每張使用中、設了結帳日的卡一格（呼叫數見第 2 節），寬度夠就排成幾欄。進行中的一期（含今天的那一期）一行：繳款日與「本期消費」（這一期卡被扣的款，每個標的一個）；最近結帳的一期，**在它的繳款日還沒過（今天或之後）而且有款項時**也列出一行，寫「期末餘額」（結帳時欠的）。繳款日是 `CardStatementSummary.DueOn`（沒有繳款日的卡寫「—」）。帳單只算已確認的款項，所以全是草稿時每張卡只有繳款日，卡片下面說一次「沒有金額的，是還沒有已確認的款項」，不在每一格寫。卡欠錢是常態，不用紅色。沒有設結帳日的卡不在這裡（信用卡帳單頁說它們沒有帳單）；沒有這樣的卡就沒有這張卡片。
  - **圖**：最近十二個月每月的支出（`GetSpendingTrend`，到今天所在的月為止，這個月是橘色的那一根，每根連到那個月的支出頁）與本月支出最多的類別（`GetSpending` 的 `TopLevel` 前五個，use case 的順序，最大的在前；超過五個時連結寫「查看全部類別」，其餘在支出頁）。**只用已確認的數字**：每個月都是零就不畫十二根空的柱子，這個月沒有支出就不畫橫條，各說「還沒有已確認的支出」。圖有 `<title>`/`<desc>`（寫了每一根的數字）；十二個月的數字還在柱狀圖下面折起來的表裡（`<details>`），橫條的數字畫在條上。
- **交易**：一頁 100 筆，超過時有上一頁、下一頁；篩選與月份的連結都保留其他篩選；帳戶篩選除了帳戶還有「沒有帳戶的交易」（`account=none`）。狀態篩選列出有那個狀態的交易：分期計畫的各期是各自的交易，草稿計畫的各期也是草稿，照列；只有草稿頁連過來的清單帶 `periods=none`，分期計畫只列起點（和草稿頁的筆數一樣），清單上方有一行字說明並附「連各期一起列」的連結，表單與月份的連結也保留它。一列的標題是說明（沒有說明就取第一個有備註的分錄的備註，再沒有取類別，最後取種類；太長時列表只顯示兩行，連結的 `title` 有完整的字），列標題（`<th scope="row">`）就只有標題；標題下面的細節是自己的一格，依序是商家、類別、種類、分期的第幾期、帳戶，標題已經是的不重複，後面接領域與專案的晶片；入帳日只在有填、而且和交易的日期不同時才寫在日期下面。金額是每個帳戶的增減（帳戶、未到期分期、往來的順序找第一種有的）；金額不是帳戶的增減時（未到期分期、往來）一律寫出它是什麼（「好銀行信用卡・未到期分期」「往來・Bob」），不只在有好幾筆金額時，這個說明排在金額上面，長的帳戶名不會把金額擠出欄位。草稿的列有虛線邊與底色，並有「草稿」標籤；已作廢的列劃線。排版與斷點見第 8 節。
- **交易明細**：每個分錄是一列，項目名稱由種類與帳簿決定（支出裡的 `expense` 分錄是「主要金額」，其他種類的是「手續費」，分期的是「利息」，對帳的是「未記錄」；支出裡正的 `dealing` 是「分攤」，負的是「往來（我欠對方）」），折扣是它所屬分錄之後的一列，不影響支出。項目與簿、種類、狀態、HTTP 狀態都用 `domain/model` 的常數與 `net/http` 的常數，不寫字串。
- **草稿**：用 `GetDraftSummary`，數字都是它的，頁面照寫。一筆草稿是 `ConfirmTransactions` 一次確認的單位：分期計畫算一筆（它的起點，在起點那個月），各期不另外算。金額是「如果這些草稿今天全部確認，帳戶的餘額今天會有的變動」：日期在今天之後的草稿與還沒到期的分期各期要到那一天才會影響餘額，所以不在金額裡（筆數照算）。帳戶的列包含轉帳進出這個帳戶的部分，一筆草稿動到兩個帳戶（轉帳）時兩邊各算一筆，所以一筆自己帳戶之間的轉帳在兩個帳戶的列各出現一次；月與總數的流出和流入不含它，那是「自己帳戶之間的轉帳」那一列，寫筆數與這些錢（use case 的 `OwnTransferAmounts`，以負號寫在流出與流入，淨額為 0，不用損失的顏色）：每一欄的各帳戶的列加上這一列，剛好是「這個月合計」，網頁的測試把表上的數字加起來驗證。草稿屬於一個帳戶，是它有分錄到那個帳戶（任何簿，所以消費分期的起點算在那張卡），這和交易頁的帳戶篩選同一個定義；沒有任何帳戶分錄的（對象先付、記成往來的支出）自成「沒有帳戶的草稿」一列，連到 `account=none`。每一組連到該月該帳戶的草稿清單（帶 `periods=none`，計畫只列起點），那份清單列的就是它算的那些。
- **信用卡帳單**（帳單頁，`/app/cards`）：帳單總覽的範圍是「今天往前十三個月」到「今天往後 31 天」，從中取進行中的一期（含今天的那一期）與最近十二期已結帳的（首頁的信用卡卡片只要接下來要繳的，範圍小得多，見上面總覽的卡片）。一張帳單的「依類別的消費」是 `GetCardStatement` 的 `Charges`：這一期卡被扣的款，每筆交易的扣款依它各行的順序分給各行：支出的行依頂層類別；手續費與分期利息也是支出的行，所以在它們自己的類別，與支出頁同一個，但手續費只有付它的是這張卡才算（轉帳的手續費由銀行付，不是這張卡被扣的款）；我替別人付的行，只有支出裡的才是「分攤」，用卡付的往來（借錢給對方、替對方墊的錢）不是；不夠解釋的是「其他」（轉帳、往來、分期的本金）。每個標的一張圖與一張表，加起來等於那一期的「本期消費」。頁面只寫 use case 分好的各行，合計取自帳單的數字。
- **預算**：領域用 `GetAreaBudgets` 該月的狀態，專案用 `GetProjectBudgets`（整個專案一個總額，不分月，頁面有一行字說專案不隨月份改變；只讀屬於專案的支出，不讀整個帳本）。超支與每一個分配的「超過分配」是 use case 的 `Over`（已花大於預算或分配，剛好花完不算），頁面不比較。沒有預算的領域只顯示已花。
- **支出**：「已花」與預算同一個定義（已確認、`expense` 帳簿、本位幣金額、到今天為止）。每個頂層類別的合計、它自己的金額與子類別是 `GetSpending` 的 `TopLevel`，頁面不加總。每月合計的窗口是「到今天所在的月為止的十二個月」，標題是「最近十二個月每月的支出」；選的月份不在其中時，窗口改成到選定的月份為止，標題改成「起月 到 迄月 每月的支出」，所以選定的月份一定是其中一根，並以不同顏色標出。

## 5. 之後要加寫入的動作

網頁已經是這樣放的：handler 回傳 `(Page, error)`，`webserver` 負責驗證、標頭、方法與錯誤頁，`webserver.UserFrom(ctx)` 給出動作的人。要加一個動作（例如確認草稿），不必動現有頁面：

1. 在 `webserver.Site` 加 `Post(pattern, handler)`，並讓 `Site.methods`（現在只放行 GET 與 HEAD 的那一個地方）對有 POST 路由的路徑放行 POST；handler 要能回 303 轉址（POST 之後 GET）。
2. 在同一個地方加一個 middleware，對所有 POST 檢查請求來自本站（`Sec-Fetch-Site: same-origin`，沒有就比對 `Origin` 與 `Host`）與表單帶的 token（綁使用者與時間的 HMAC）；一處檢查，不是每個 handler 各做各的。CSP 的 `form-action 'self'` 已經允許本站的表單，不需要 JavaScript：要二次確認就多一頁確認頁。
3. 動作呼叫既有的 use case（`ConfirmTransactions`、`DiscardDraft`、`VoidTransaction`……），經 `Ports` 注入；依架構慣例第 8 節帶冪等鍵（表單渲染時產生，放在隱藏欄位），來源記為網頁、身分用 `UserFrom`。

## 8. 視覺規則

交易頁（`/app/transactions`）與總覽（`/app/`）已經照這些規則排好，之後各頁（草稿、帳單、預算、支出）統一時照它們做。樣式表只有一份（`pkg/webserver/assets/app.css`），沒有 inline style，不從網路載入字型或圖片。

- **風格**：券商 App 的樣子：深色為主，亮色是同一組 token 的亮色版，兩個主題都要看過；表面克制，數字大、靠右、用等寬數字（系統字型加 `font-variant-numeric: tabular-nums`）；金額以正負號與顏色兩個線索表示增減，顏色只是第二個線索。
- **Token**（`:root` 與深色的 `:root` 各一份；新的顏色先加成 token，兩個主題都要有）：`--bg`、`--surface`、`--surface-2` 是頁面、卡片與再上一層；`--text`、`--muted`（日期、次要文字、金額的幣別）；`--border`（分隔線）與 `--control-border`（下拉與按鈕的邊：它們是控制項，邊對它旁邊的底至少 3:1，實測亮色最低 3.1、深色最低 3.2）；`--pos`（增加）與 `--neg`（紅，見下）；`--accent` 與它上面的字 `--on-accent`；`--draft-bg`、`--draft-edge`（草稿的底與虛線邊）、`--void-text`（作廢）、`--ok-bg`；`--hover`（列的滑過與聚焦，疊在原本的底色上，草稿的列也看得出）；`--focus`。文字與它的底（含滑過）至少 4.5:1，兩個主題實際最低約 5.0:1。
- **金額**：`.amt`，負數 `.neg`，幣別代碼 `.unit` 比數字小而淡。交易的列（`.tx-move`）增加是 `--pos`（綠），減少是一般文字色加負號，**不用紅色**：一串花費不是一串損失；正負號還在，顏色只是第二個線索。紅色（`--neg`、`--over`）留給錯誤與超支，作廢用灰色加刪除線，也不用紅。**總覽怎麼用紅色**（#32 第 3 步定的）：帳戶的餘額（大數字、各組的小計、每一列）只有有已確認基礎的負數是紅的，因為帳戶欠多少（信用卡、貸款、透支）是真的負債；不是損失的數字一律不用紅色：本月支出、草稿的變動、信用卡卡片裡的帳單與本期消費；往來的負數（我欠對方）仍是紅的。其他頁（草稿、帳單、預算、支出）現在還用 `--neg` 標負數，統一時（#32 第 4 步）照這條與上一條改。
- **元件**：藥丸 `.pill`（`pill-draft`、`pill-confirmed`、`pill-void`）說狀態，文字是狀態，圓點的顏色只是重複；晶片 `.chip` 是領域與專案的淡色小標籤，接在細節那一行的後面，不另開一欄（沒有領域與專案的列就不為它們留空），專案寫成「專案：名稱」（冒號後有 `<wbr>`），領域的晶片前有只給讀屏軟體的「領域：」；篩選是一條工具列 `.filters`，每個篩選一個有標籤的欄位，下拉的箭頭用漸層畫，因為 CSP 連 `data:` 的圖都不讓進來；月份與分頁的按鈕是圓角的。其他頁還在用舊的 `.badge` 與 `.stack`（每格前面寫欄名的卡片），統一時換成這兩個元件與下面的列表。
- **預覽餘額**（總覽，第 4 節）：只用這一節已有的 token 與元件，沒有新的顏色。「帳戶餘額」旁的標籤是藥丸 `.pill.pill-draft`，文字是「預覽（含 N 筆草稿）」（草稿色是「這些數字含草稿」的線索，圓點只是重複），帳戶表的金額欄的欄名也寫「餘額（預覽）」，因為表一長，標題已經捲出畫面；它的說明是大數字下面的 `.hero-note.muted.small`，沒有有底色的框（總覽已經沒有 `.note-draft`：草稿是一張普通的卡片，頁面上沒有琥珀色的框，只有藥丸）。每個數字下面的「已確認 x」或「尚未確認」是 `.line.muted.small`，已確認的數字帶負號、不設 `.neg`（沒有損失的顏色：它是對照，不是餘額）；那一行裡的幣別代碼和字一樣大（`.line.muted.small .unit` 是 `1em`，不是 `.unit` 的 `0.8em`：`0.8em` 套在小字上只有約 10.9px，是註腳的大小）；一個數字與它的已確認那一行是一組，同一格裡下一組隔 0.4rem（`.num .line.muted + .line`，標籤列的 `.tile .line.muted + .line` 也是），否則多標的的帳戶分不出哪一行是哪個數字的。**紅色只給有已確認基礎的負數**：整個是草稿的數字（「尚未確認」）用一般文字色加負號，整個帳本都是草稿時才不會紅一片；其餘有已確認基礎的負數用 `--neg`（紅）：上一條「不用紅色」是交易的列的規則（花費不是損失），帳戶欠多少是真的負債，所以在這裡紅色留著。**餘額的表在 30rem 以下**（手機）帳戶名在上、金額在下：`table.balances` 在 `@media (max-width: 30rem)` 把表的各部分改成區塊，欄標題只留給讀屏軟體，與 `.stack` 同一個作法，因為帳戶名是自由文字，旁邊有「已確認」那幾行時，在 320px 它被擠成一兩個字一行；標記上的 `role` 讓它仍是一張表；這個表在卡片裡，卡片左右的 1.1rem 就是列的 padding（`.in-card .balances tr`），格子自己沒有。**說明裡的連結與詞整個留著**：草稿卡與預覽的說明是自由文字，行尾會在任何一個字後折行（不能用 `keep-all`，見下面「中文不一字一行」），所以「查看草稿」的連結與「未到期分期」這個詞用 `.nowrap` 包著，不會被切成「查看／草稿」「未到期分／期」。
- **卡片**（總覽，第 4 節）：卡片 `.card` 是比頁面高一層的表面（`--surface`），一條 `--border` 的細線、14px 的圓角，沒有陰影也沒有漸層；沒有新的 token。標題 `.card-title` 是 0.8125rem、淡色（`--muted`）的小字，去哪裡的連結（「查看支出」`.card-link`）與標題同一行靠右（`.card-head`）；卡片裡最大的是數字：`.stat-figure` 1.75rem 粗體、等寬數字，幣別代碼小而淡；說明是 `.muted.small`；沒有資料時是一行淡色的字（`.stat-empty`），不是一個 0.00。**大數字**（`.hero`）：`.hero-figure` 是 `clamp(1.75rem, 8vw, 3rem)`、粗體、等寬數字；數字不在中間折行，太寬時折的是幣別代碼（`.hero-figure .amt` 放掉 `nowrap`，數字本身沒有空白可折）。它下面是「已確認 x」或「尚未確認」與未到期分期（`.hero-sub`），再下面是其他標的的一排（`.tiles`，每個 `.tile` 一個數字，代碼在數字後面，有已確認的對照時在它下面），用一條細線隔開。同一個 `.tiles` 也是帳戶組標題右邊的小計：40rem 以上靠右（放不進名稱那一行時折到名稱下面，仍靠右，在金額那一欄的上方），手機上靠左。**一排卡片**（`.cards`）：`flex-wrap`，每張卡片 `flex: 1 1 15rem`，一排放得下幾張就放幾張，同一排等高；最後一排只有一兩張時，它們撐滿那一排，不留空洞（`grid` 的 `auto-fit` 做不到：它在最後一排留下空的格子，1024 寬的卡片會是三加一個空洞）。**信用卡**（`.payments`）不在那一排裡，是自己一張與頁面一樣寬的卡片：卡有好幾張時，放在一排裡它會把整排撐得很高，旁邊的卡片空掉一大半（用真實的帳本看過才改）；每張卡一格（`.due-list`：`grid`，`repeat(auto-fill, minmax(min(24rem, 100%), 1fr))`，格子上面一條細線），寬度夠就排成幾欄；24rem 是一格放得下「上一期　繳款日 …　期末餘額 …」一行的寬度（18rem 時 1280 寬排成三欄，金額折到下一行，看起來亂），所以 1280 寬是兩欄、每一期一行；`min(24rem, 100%)` 讓 320px 的手機上一欄不會比卡片還寬（只寫 `24rem` 時頁面會橫向捲動，視覺檢查量到的）。**兩張圖**（`.charts`）：52rem 以上並排，以下一張一張；圖的畫布是 360 單位、字 12 單位，所以圖在卡片裡最寬 30rem（`.card .chart`），再寬字就太大（1280 寬時整張卡片寬的柱狀圖，月份標籤有 23px）。**帳戶的組**（`.groups`）：60rem 以上兩欄，用 CSS 多欄（`columns: 2`）讓組依高度自己落在有空的那一欄，DOM 的順序（銀行、信用卡、現金……）就是讀的順序；每組包在一個 `.slot`（`break-inside: avoid`）裡，卡片之間的空白是它的 `padding-bottom`，不是卡片的 `margin`：WebKit 會把欄尾的 margin 帶到下一欄的頂端，第二欄就比第一欄低 1rem（量過）。組裡的表是 `.table-wrap.in-card`（沒有自己的框）。
- **交易的列**（`.tx`）：一列的格子依序是日期、標題（`<th scope="row">`，就只有標題）、細節（`<td class="tx-sub">`：商家、類別、種類、分期、帳戶與領域／專案的晶片）、狀態、金額。標題與細節排在同一欄，一上一下，但是各自的一格，所以讀屏軟體念列標題時只念標題。標題最多兩行（`title` 有完整的字，完整的內容在交易頁）；每列一個連結，就是標題，聚焦時有 3px 的框。卡片的排法讓整張卡片都是它的點擊範圍，所以卡片裡的標題有底線（沒有滑鼠的連結要有看得出是連結的線索），表裡滑過才有。
- **斷點**：一列都是一個 grid，格子用名字放進去，表頭與列用同一組欄寬，所以對得齊。60rem 以上是表的樣子：四欄（日期 7rem、交易，其餘寬度、標題上細節下，狀態 5.25rem、金額 10.5rem），欄標題看得到（「細節」只給讀屏軟體）。60rem 以下每一列是一張卡片：標題在左、金額在右（金額欄最多佔卡片的 45%），細節在下面，用整張卡片的寬度（長的帳戶名與領域、專案的晶片才排得進同一行），日期與狀態在最下面一行；欄標題只留給讀屏軟體，標記上的 `role` 讓它仍是一張表。篩選的工具列 48rem 以上排成一列，以下帳戶一列、狀態與種類並排；40rem 以下月份的按鈕縮小，讓上個月、月份、下個月排得進一列。
- **中文不一字一行**：標題是自由文字，照中文的方式折行，欄寬與卡片的排法保證它不會窄到一字一行；名稱（商家、類別、帳戶、領域、專案、金額的標籤）用 `word-break: keep-all` 整個留著，一個東西的幾個名字之間（`、` 之後有 `<wbr>`）與東西之間才折行；只有比整個欄還寬的名稱才用 `overflow-wrap: anywhere` 在最後硬折。自由文字不用 `keep-all`：它只剩空白處能折，WebKit 會把「。」擠到行首。
- **可及性**：列標題只有標題；標題的連結被截成兩行的是連結自己，所以聚焦框不會被截掉；列在滑過與聚焦時變色；下拉與按鈕的邊用 `--control-border`；強制色彩模式下藥丸與晶片有框；沒有動畫，沒有 JavaScript。
