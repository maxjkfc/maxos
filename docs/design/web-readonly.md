# 唯讀網頁設計

`maxos serve` 在 `/app/` 底下提供一組唯讀的網頁，看帳本裡的資料與圖表。用語以 `CONTEXT.md` 為準，分層與依賴以 `docs/architecture-conventions.md`（尤其第 11 節）為準。本檔記錄這組網頁的決定；與程式碼不一致之處以程式碼為準，並回頭修正本檔。

## 1. 範圍

- 只讀。之後頁面要能做操作（確認、記帳……），所以結構上留好位置（第 5 節），但現在沒有任何寫入的路徑。
- 與 `/mcp` 同一個 Cloudflare Access：沒有未驗證的入口，沒有關掉驗證的開關。
- 聊天式的查詢（MCP 的查詢工具）留給 M3，網頁與它無關。
- 介面是繁體中文，詞彙照 `CONTEXT.md`（帳戶、餘額、交易、種類、草稿、類別、領域、專案、預算、分配、往來、對象、帳單、結帳日、繳款日、入帳日、未到期分期、未記錄……），不用它的 `_Avoid_` 欄列的詞：`glossary_test.go` 從 `CONTEXT.md` 讀出每個 `_Avoid_` 的詞（名字是別的詞條、或是種類的名字的除外），每個測試取得的每一頁都對照它，連 404 與 400 的頁面也是。

## 2. 路由

每條路由都在 Access verifier 後面；沒有 token 的請求得到和 `/mcp` 一樣的 `401 unauthorized`。

| 路徑 | 頁面 | 參數 | 呼叫的 use case（另外每頁讀一次需要的參考清單） |
|---|---|---|---|
| `/app/` | 總覽：各機構的餘額（有草稿等著確認時是預覽餘額）、未到期分期、往來、等著確認的草稿 | | `GetPreviewBalances`、`GetDealings`、`ListInstalmentPlans`、`GetDraftSummary` |
| `/app/transactions` | 一個月的交易，可篩帳戶、狀態、種類 | `month=YYYY-MM`、`account`（帳戶 id，或 `none`：沒有帳戶的交易）、`status`、`kind`、`periods`（只能是 `none`：分期計畫只列起點，不列各期）、`page` | `ListTransactions`（一頁 100 筆） |
| `/app/transactions/{id}` | 一筆交易的所有部分、標籤、所屬的分期計畫 | | `GetTransaction`、`GetInstalmentPlan`（屬於計畫時） |
| `/app/drafts` | 草稿依月份再依帳戶分組，附筆數與金額 | | `GetDraftSummary` |
| `/app/cards` | 信用卡：進行中的一期與最近結帳的十二期 | | `ListCardStatements`（每張設了結帳日的卡一次） |
| `/app/cards/{account}` | 一張帳單：數字、交易（舊的在前）、依類別的消費 | `closing=YYYY-MM-DD`（帳單裡的任何一天，預設今天） | `GetCardStatement` |
| `/app/budgets` | 領域與專案的預算、已花、分配、未分配 | `month=YYYY-MM` | `GetAreaBudgets`、`GetProjectBudgets` |
| `/app/spending` | 這個月依類別的支出，最近十二個月的支出合計 | `month=YYYY-MM` | `GetSpending`、`GetSpendingTrend` |
| `/app/static/app.css` | 唯一的樣式表 | | |
| `/app` | 轉到 `/app/`（驗證之後才轉） | | |

- `month` 不給就是今天所在的月（時區是 `MAXOS_TIMEZONE`，今天只來自時鐘 port）。查詢字串用 `url.ParseQuery` 讀：壞的跳脫、分號，與一頁收的參數給了不只一個值，都是 400 頁面；不合法的參數（不是月份、年份在 1900 到 2999 之外、不是 id、`page` 不是 1 到 10000）也是 400 頁面，說明是哪個參數該是什麼，不重複收到的值；不存在的 id、不是帳單的帳戶是 404 頁面；其他方法是 405；use case 失敗是 500 頁面，不說原因（記在日誌）。
- 一頁的 use case 呼叫數固定：列出來的東西一次取得，參考清單（帳戶、機構、標的、類別、領域、專案、對象、標籤）各讀一次，含已封存的，因為舊交易指著它們。信用卡總覽每張設了結帳日的卡呼叫一次，那是卡的張數，不是帳本的筆數。`TestPagesIssueAFixedNumberOfCalls` 用一列與四百列的世界各讀每一頁，呼叫要完全一樣。
- 新增的讀取在 finance 的 `port/in`：`GetSpending`（頂層類別的合計）、`GetSpendingTrend`（「已花」與預算同一個定義，見 `m1-ledger.md` 第 5 節的「網頁用的讀取」）、`GetDraftSummary`、`GetPreviewBalances`（總覽的餘額：已確認的餘額加上草稿今天全部確認會有的變動，持有與未到期分期兩個數字，連同草稿的筆數與有沒有已確認的，一次讀取；取代總覽原本的 `GetBalances`，所以總覽的呼叫數不變）、`GetCardStatement` 的 `Charges`、預算的每個分配的 `Over`，以及 `ListTransactions` 的 `Kind` 與 `WithoutAccount` 篩選。

## 3. 結構與安全

```
cmd/serve.go                      newHTTPHandler：安全標頭與 Access verifier 在最外面，裡面是 /mcp 與 /app/
cmd/web.go                        WebModule：各 context 的 registrar 收進 Fx 的 web.registrars；填 adapter 的 Ports 的 Fx struct 也在這裡
pkg/webserver                     Registry/Site：版面、導覽、錯誤頁、標頭、格式；不認識 context
pkg/svgchart                      圖表：資料進、SVG 出的純函式
app/finance/adapter/in/web        finance 的頁面：handler、view、templates/*.gohtml
internal/webtest                  測試用的 Access 替身（自簽金鑰）
```

- **守門**：`newHTTPHandler` 最外面是 `webserver.Secure(verifier.Middleware(mux))`，所以 mux 自己回的轉址與 404 也在驗證後面：沒有 token 的請求只得到 401，每個回應都帶標頭。`Registry.Pages(userOf, guard)` 的 guard 與 userOf 仍是必填，頁面自己也被它包住，所以頁面不靠被掛在哪裡；顯示的使用者是 token 的 email（服務 token 是 `service:<id>`）。只認 `Cf-Access-Jwt-Assertion` 標頭，不認 `CF_Authorization` cookie。沒有任何繞過驗證的開關；測試用 `internal/webtest` 的自簽金鑰，視覺檢查也是（第 7 節）。**`/mcp` 也帶這些標頭，而且 `Cache-Control` 是 `no-store, no-transform`**：go-sdk 在 `tools/call` 的 200 回應裡把它改成 `no-cache, no-transform`，蓋掉 `Secure` 設的 `no-store`，所以 `/mcp` 另外包一層 `webserver.NoStore`，在回應送出標頭的那一刻（`WriteHeader`、第一次 `Write`、`Flush`，或 handler 什麼都沒寫就返回）把它設回去；它實作 `Unwrap`，SDK 串流（SSE）的 flush 照常，其餘四個標頭不動。**`OPTIONS *` 也在驗證後面**：`net/http` 自己會在 handler 之前回它 200、沒有任何標頭，所以 server 設了 `DisableGeneralOptionsHandler`（`cmd.NewHTTPServer`，`serve` 與測試用同一個）：沒有 token 是 401 並帶標頭，有 token 是 mux 回的 400。被拒絕的請求記在日誌裡的路徑與原因最多 200 個字元（超過的接 `…`，另記原本的位元組數），客戶端給的 900 KB 路徑不會原樣寫進日誌。
- **標頭**（`webserver.Secure`，每個回應，包括 401）：`Content-Security-Policy: default-src 'self'; script-src 'none'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`（`/mcp` 是 `no-store, no-transform`）、`X-Frame-Options: DENY`。沒有 inline script 也沒有 inline style（進度條與圖表是 SVG 元素，以 class 上色），沒有 JavaScript、CDN、字型或圖片的外部請求。
- **方法**：只有 GET 與 HEAD，其他一律 `405` 並帶 `Allow: GET, HEAD`。
- **圖表**是伺服器產生的 inline SVG（`pkg/svgchart`：橫條圖、直條圖、進度條），所有文字都經過跳脫，連結只收站內路徑，幾何用 decimal 算，沒有浮點數。直條圖上高亮欄的數字畫在它蓋到的欄裡最高的那一根的上方，不壓在比它高的鄰欄上（數字的寬度由字數估計，估得寬一點；超出左右邊界時靠該欄的邊）。每張圖旁邊都有一張同樣數字的表，表是依據，圖是它的樣子；SVG 的 `<title>`/`<desc>` 也寫了同樣的數字給讀屏軟體。
- **可及性與版面**：真的 `<table>`、`<th scope>`、`<caption>`，數字靠右並用等寬數字，負數以負號（U+2212）標示，顏色只是第二個線索；超支同時有文字與顏色；亮色與暗色跟著系統（`prefers-color-scheme`），桌面寬度圖與表並排。手機寬度（40rem 以下）每一列排成一張小卡片，每格前面寫欄名（`data-label`；欄標題留給讀屏軟體，標記上的 `role` 讓它仍是一張表）；欄位多的表在手機與桌面之間保持寬度，在框內橫向捲動。交易頁的列表是例外，它有自己的排法，也是之後各頁要統一成的樣子（第 8 節）。
- **金額**依標的的小數位數、千分位；**日期**是帳本裡的日曆日（不轉時區），**時刻**（建立、確認、作廢、發生時間）以 `MAXOS_TIMEZONE` 顯示。

## 4. 各頁怎麼排、怎麼算

網頁只排版，數字是 use case 的（架構慣例第 11 節）。有取捨的地方：

- **總覽**：餘額依機構分組，沒有機構的最後；一個標的一行，未到期分期是另一行（負的，和餘額同號）。有草稿等著確認時，餘額區是預覽餘額（下一條）。持有與未到期分期都是零、也沒有已確認的部分的帳戶收進摺疊的清單，已封存又沒有餘額的不列。未到期分期的表列的是分期的本金，所以是正數（欄名「已到期的本金」「未到期分期」），旁邊一行字說明它在餘額裡是負數、另外列出。往來為正是「對方欠我」，為負是「我欠對方」，用文字說出來，全部為零的對象收進摺疊清單。草稿的表是「如果這些草稿今天全部確認，帳戶的餘額今天會有的變動」，另有一行「自己帳戶之間的轉帳」的筆數。
- **預覽餘額**（總覽的餘額區，有草稿等著確認時）：帳本裡全是草稿時（匯入之後），已確認的餘額是空的，整區看起來像沒有資料；預覽餘額讓人看到「如果草稿都確認了，各帳戶今天會有多少」，並標明那是預覽。數字是 `GetPreviewBalances` 的，頁面不加總、不判斷（架構慣例第 11 節）。定義只有一個，對每個帳戶、每個標的，`GetBalances` 的兩個數字（持有 ＝ `Quantity`，未到期分期 ＝ `UnbilledInstalment`）各一份：**預覽 ＝ 今天的已確認數字（`GetBalances` 今天的）＋ 所有草稿今天全部確認會有的變動**。變動是狀態為草稿、`occurred_on` 不晚於今天的交易的分錄加起來，各在自己的帳戶（分期計畫的各期在資料庫裡是各自的草稿，也算）：`account` 帳簿的分錄加進持有，`instalment` 帳簿的分錄加進未到期分期。持有的變動與草稿區同一條規則（`GetDraftSummary` 的金額，各帳戶所有月份的淨額加起來）：日期在今天之後的草稿與還沒到期的分期各期不算（到那一天才算），作廢的交易不算，沒有帳戶的草稿（對象先付的支出）不動任何帳戶；轉帳進出的兩個帳戶都算，各自的預覽都動，全部帳戶加起來不動（手續費除外）。未到期分期的變動是草稿計畫的本金：消費分期的起點讓那張卡欠整筆本金（未到期分期，持有不動），各期扣款日到了，那一期的本金從未到期分期移到持有，利息也進持有；帳單分期的起點把帳單還清（持有），同一筆轉成欠的本金（未到期分期），兩個數字的變動互相抵銷。只算持有的預覽會讓卡欠的比確認之後少：確認之後 `GetBalances` 的未到期分期才有這筆本金。四個測試把定義釘住（一條 SQL，`ListPreviewBalances`，與 `model.SummarizeDrafts` 是兩種寫法的同一個規則）：①確認全部草稿之後，每個帳戶每個標的的 `GetBalances` 兩個數字，就是確認前的預覽（含草稿的消費分期與帳單分期）；②每個帳戶持有的草稿部分，是 `GetDraftSummary` 各月份該帳戶的淨額加起來；③所有帳戶持有的草稿部分，每個標的加起來等於 `GetDraftSummary` 的總淨額（自己帳戶之間的轉帳淨額為 0）；④草稿的筆數就是 `GetDraftSummary` 的 `Count`。讀取是一份快照：餘額（一條語句）與筆數（`CountDrafts`，分期計畫算一筆）在 `WithinSnapshot` 裡讀，一筆草稿在讀的當中被確認，只會在已確認或草稿其中一邊，不會兩邊都有或都沒有。
  - **什麼時候是預覽**：`GetPreviewBalances` 的 `DraftCount` 不為 0；它與餘額是同一次讀取，所以標題、說明與每個數字說的是同一件事，頁面不自己數。它與草稿區的筆數是同一個定義（分期計畫算一筆，日期在今天之後的也算，它們只是還沒影響數字）。餘額區的標題旁是藥丸「預覽（含 N 筆草稿）」，金額欄的欄名是「餘額（預覽）」；標題下一行字說明：已確認的餘額，加上這些草稿今天全部確認後會有的變動，草稿確認之後這裡會換成實際的餘額，並連到草稿頁。全都是草稿時（`HasConfirmed` 為假，匯入之後的樣子）改說「還沒有已確認的餘額，這些數字全是草稿」。沒有草稿時照舊：標題只有「餘額」，欄名也是「餘額」，沒有任何預覽的字，沒有「已確認」那一行。
  - **一個數字**：主數字是預覽。use case 給每個數字一個 `Basis`，頁面照它寫：`confirmed`（草稿沒動它）什麼也不加；`both`（有已確認的部分，草稿動了它）下面一行淡色小字「已確認 x」；`drafts`（沒有已確認的部分，整個是草稿的）下面一行「尚未確認」，不寫一排 0.00。已確認的數字是對照，不用紅色。**紅色只給有已確認基礎的負數**（`confirmed` 與 `both`，與沒有草稿時一樣）：整個是草稿的負數保留負號，用一般文字色，因為還沒有任何已確認的錢被花掉，整個帳本都是草稿時負數很多，標紅是一片假警報。預覽的持有是零、而草稿抵銷了已確認的部分時（已確認 500、草稿 −500），仍列出一行「0.00　已確認 500.00」，不收進摺疊，也不被只剩下的未到期分期那一行取代；收進摺疊的「餘額皆為零的帳戶」的是預覽與已確認都是零的帳戶。
  - **與草稿區**：草稿的表不變，它的淨額就是餘額區每個持有數字的「預覽減已確認」依標的加起來（頁面的測試把頁面上的數字加起來驗證）。**未到期分期不在這個相等裡**：草稿的表只算 `account` 帳簿，分期計畫的本金不是帳戶的收支，它列在帳戶那一行「未到期分期」（那一行的草稿部分是 `instalment` 帳簿的分錄），所以草稿區的說明這麼說，並寫明還沒到期的分期各期與日期在今天之後的草稿，要到那一天才影響餘額，預覽也不含。草稿區開頭一句是「草稿確認後才生效：預算、報表和已確認的餘額都不含它們，上面「預覽」的餘額是把它們算進去的樣子」。未到期分期的表（`ListInstalmentPlans`）只列已確認的計畫，預覽時表的說明加一句：還是草稿的計畫確認之後才列在這裡，它們還沒到期的本金已經算進帳戶的「未到期分期」。
- **交易**：一頁 100 筆，超過時有上一頁、下一頁；篩選與月份的連結都保留其他篩選；帳戶篩選除了帳戶還有「沒有帳戶的交易」（`account=none`）。狀態篩選列出有那個狀態的交易：分期計畫的各期是各自的交易，草稿計畫的各期也是草稿，照列；只有草稿頁連過來的清單帶 `periods=none`，分期計畫只列起點（和草稿頁的筆數一樣），清單上方有一行字說明並附「連各期一起列」的連結，表單與月份的連結也保留它。一列的標題是說明（沒有說明就取第一個有備註的分錄的備註，再沒有取類別，最後取種類；太長時列表只顯示兩行，連結的 `title` 有完整的字），列標題（`<th scope="row">`）就只有標題；標題下面的細節是自己的一格，依序是商家、類別、種類、分期的第幾期、帳戶，標題已經是的不重複，後面接領域與專案的晶片；入帳日只在有填、而且和交易的日期不同時才寫在日期下面。金額是每個帳戶的增減（帳戶、未到期分期、往來的順序找第一種有的）；金額不是帳戶的增減時（未到期分期、往來）一律寫出它是什麼（「好銀行信用卡・未到期分期」「往來・Bob」），不只在有好幾筆金額時，這個說明排在金額上面，長的帳戶名不會把金額擠出欄位。草稿的列有虛線邊與底色，並有「草稿」標籤；已作廢的列劃線。排版與斷點見第 8 節。
- **交易明細**：每個分錄是一列，項目名稱由種類與帳簿決定（支出裡的 `expense` 分錄是「主要金額」，其他種類的是「手續費」，分期的是「利息」，對帳的是「未記錄」；支出裡正的 `dealing` 是「分攤」，負的是「往來（我欠對方）」），折扣是它所屬分錄之後的一列，不影響支出。項目與簿、種類、狀態、HTTP 狀態都用 `domain/model` 的常數與 `net/http` 的常數，不寫字串。
- **草稿**：用 `GetDraftSummary`，數字都是它的，頁面照寫。一筆草稿是 `ConfirmTransactions` 一次確認的單位：分期計畫算一筆（它的起點，在起點那個月），各期不另外算。金額是「如果這些草稿今天全部確認，帳戶的餘額今天會有的變動」：日期在今天之後的草稿與還沒到期的分期各期要到那一天才會影響餘額，所以不在金額裡（筆數照算）。帳戶的列包含轉帳進出這個帳戶的部分，一筆草稿動到兩個帳戶（轉帳）時兩邊各算一筆，所以一筆自己帳戶之間的轉帳在兩個帳戶的列各出現一次；月與總數的流出和流入不含它，那是「自己帳戶之間的轉帳」那一列，寫筆數與這些錢（use case 的 `OwnTransferAmounts`，以負號寫在流出與流入，淨額為 0，不用損失的顏色）：每一欄的各帳戶的列加上這一列，剛好是「這個月合計」，網頁的測試把表上的數字加起來驗證。草稿屬於一個帳戶，是它有分錄到那個帳戶（任何簿，所以消費分期的起點算在那張卡），這和交易頁的帳戶篩選同一個定義；沒有任何帳戶分錄的（對象先付、記成往來的支出）自成「沒有帳戶的草稿」一列，連到 `account=none`。每一組連到該月該帳戶的草稿清單（帶 `periods=none`，計畫只列起點），那份清單列的就是它算的那些。
- **信用卡帳單**：總覽的範圍是「今天往前十三個月」到「今天往後 31 天」，從中取進行中的一期（含今天的那一期）與最近十二期已結帳的。一張帳單的「依類別的消費」是 `GetCardStatement` 的 `Charges`：這一期卡被扣的款，每筆交易的扣款依它各行的順序分給各行：支出的行依頂層類別；手續費與分期利息也是支出的行，所以在它們自己的類別，與支出頁同一個，但手續費只有付它的是這張卡才算（轉帳的手續費由銀行付，不是這張卡被扣的款）；我替別人付的行，只有支出裡的才是「分攤」，用卡付的往來（借錢給對方、替對方墊的錢）不是；不夠解釋的是「其他」（轉帳、往來、分期的本金）。每個標的一張圖與一張表，加起來等於那一期的「本期消費」。頁面只寫 use case 分好的各行，合計取自帳單的數字。
- **預算**：領域用 `GetAreaBudgets` 該月的狀態，專案用 `GetProjectBudgets`（整個專案一個總額，不分月，頁面有一行字說專案不隨月份改變；只讀屬於專案的支出，不讀整個帳本）。超支與每一個分配的「超過分配」是 use case 的 `Over`（已花大於預算或分配，剛好花完不算），頁面不比較。沒有預算的領域只顯示已花。
- **支出**：「已花」與預算同一個定義（已確認、`expense` 帳簿、本位幣金額、到今天為止）。每個頂層類別的合計、它自己的金額與子類別是 `GetSpending` 的 `TopLevel`，頁面不加總。每月合計的窗口是「到今天所在的月為止的十二個月」，標題是「最近十二個月每月的支出」；選的月份不在其中時，窗口改成到選定的月份為止，標題改成「起月 到 迄月 每月的支出」，所以選定的月份一定是其中一根，並以不同顏色標出。

## 5. 之後要加寫入的動作

網頁已經是這樣放的：handler 回傳 `(Page, error)`，`webserver` 負責驗證、標頭、方法與錯誤頁，`webserver.UserFrom(ctx)` 給出動作的人。要加一個動作（例如確認草稿），不必動現有頁面：

1. 在 `webserver.Site` 加 `Post(pattern, handler)`，並讓 `Site.methods`（現在只放行 GET 與 HEAD 的那一個地方）對有 POST 路由的路徑放行 POST；handler 要能回 303 轉址（POST 之後 GET）。
2. 在同一個地方加一個 middleware，對所有 POST 檢查請求來自本站（`Sec-Fetch-Site: same-origin`，沒有就比對 `Origin` 與 `Host`）與表單帶的 token（綁使用者與時間的 HMAC）；一處檢查，不是每個 handler 各做各的。CSP 的 `form-action 'self'` 已經允許本站的表單，不需要 JavaScript：要二次確認就多一頁確認頁。
3. 動作呼叫既有的 use case（`ConfirmTransactions`、`DiscardDraft`、`VoidTransaction`……），經 `Ports` 注入；依架構慣例第 8 節帶冪等鍵（表單渲染時產生，放在隱藏欄位），來源記為網頁、身分用 `UserFrom`。
4. 測試：`TestOnlyGETIsServed` 要改成「只有登記了 POST 的路由接受 POST，其他仍是 405」，並加 CSRF 的拒絕案例；`cmd/` 的測試走一遍真的動作。

## 6. 刻意不顯示的

- **淨資產**：需要價格（M4、M5），所以沒有這個數字，頁面也沒有說明它在哪裡。**損益、成本、匯率變動**同理。
- 草稿的確認與捨棄、記帳、預算的設定：現在都是唯讀。
- 收件（inbox）的內容與交易的冪等鍵：不是看帳要看的東西。
- 標籤只顯示在交易明細，沒有以標籤篩選或統計：標籤「不參與任何計算，只用來篩選」，要篩選時再加。
- 分頁以外的搜尋、匯出與排序：還沒有需要。

## 8. 視覺規則

交易頁（`/app/transactions`）先照這些規則重排，之後各頁（總覽、草稿、帳單、預算、支出）統一時照它做。樣式表只有一份（`pkg/webserver/assets/app.css`），沒有 inline style，不從網路載入字型或圖片。

- **風格**：券商 App 的樣子：深色為主，亮色是同一組 token 的亮色版，兩個主題都要看過；表面克制，數字大、靠右、用等寬數字（系統字型加 `font-variant-numeric: tabular-nums`）；金額以正負號與顏色兩個線索表示增減，顏色只是第二個線索。
- **Token**（`:root` 與深色的 `:root` 各一份；新的顏色先加成 token，兩個主題都要有）：`--bg`、`--surface`、`--surface-2` 是頁面、卡片與再上一層；`--text`、`--muted`（日期、次要文字、金額的幣別）；`--border`（分隔線）與 `--control-border`（下拉與按鈕的邊：它們是控制項，邊對它旁邊的底至少 3:1，實測亮色最低 3.1、深色最低 3.2）；`--pos`（增加）與 `--neg`（紅，見下）；`--accent` 與它上面的字 `--on-accent`；`--draft-bg`、`--draft-edge`（草稿的底與虛線邊）、`--void-text`（作廢）、`--ok-bg`；`--hover`（列的滑過與聚焦，疊在原本的底色上，草稿的列也看得出）；`--focus`。文字與它的底（含滑過）至少 4.5:1，兩個主題實際最低約 5.0:1。
- **金額**：`.amt`，負數 `.neg`，幣別代碼 `.unit` 比數字小而淡。交易的列（`.tx-move`）增加是 `--pos`（綠），減少是一般文字色加負號，**不用紅色**：一串花費不是一串損失；正負號還在，顏色只是第二個線索。紅色（`--neg`、`--over`）留給錯誤與超支，作廢用灰色加刪除線，也不用紅。其他頁現在還用 `--neg` 標負數，統一時（#32 第 4 步）照這條改。
- **元件**：藥丸 `.pill`（`pill-draft`、`pill-confirmed`、`pill-void`）說狀態，文字是狀態，圓點的顏色只是重複；晶片 `.chip` 是領域與專案的淡色小標籤，接在細節那一行的後面，不另開一欄（沒有領域與專案的列就不為它們留空），專案寫成「專案：名稱」（冒號後有 `<wbr>`），領域的晶片前有只給讀屏軟體的「領域：」；篩選是一條工具列 `.filters`，每個篩選一個有標籤的欄位，下拉的箭頭用漸層畫，因為 CSP 連 `data:` 的圖都不讓進來；月份與分頁的按鈕是圓角的。其他頁還在用舊的 `.badge` 與 `.stack`（每格前面寫欄名的卡片），統一時換成這兩個元件與下面的列表。
- **預覽餘額**（總覽，第 4 節）：只用這一節已有的 token 與元件，沒有新的顏色。標題旁的標籤是藥丸 `.pill.pill-draft`，文字是「預覽（含 N 筆草稿）」（草稿色是「這些數字含草稿」的線索，圓點只是重複），金額欄的欄名也寫「餘額（預覽）」，因為表一長，標題已經捲出畫面；它的說明是標題下一行 `.muted.small`，不另開一塊有底色的框（草稿區那一塊 `.note-draft` 已經是了，頁面上有兩塊琥珀色的框就太多）。每個數字下面的「已確認 x」或「尚未確認」是 `.line.muted.small`，已確認的數字帶負號、不設 `.neg`（沒有損失的顏色：它是對照，不是餘額）；那一行裡的幣別代碼和字一樣大（`.line.muted.small .unit` 是 `1em`，不是 `.unit` 的 `0.8em`：`0.8em` 套在小字上只有約 10.9px，是註腳的大小）；一個數字與它的已確認那一行是一組，同一格裡下一組隔 0.4rem（`.num .line.muted + .line`），否則多標的的帳戶分不出哪一行是哪個數字的。**紅色只給有已確認基礎的負數**：整個是草稿的數字（「尚未確認」）用一般文字色加負號，整個帳本都是草稿時才不會紅一片；其餘的負數仍用 `--neg`（紅），上一條「不用紅色」在總覽統一時（#32 第 3 步）一起改。**餘額的表在 30rem 以下**（手機）帳戶名在上、金額在下：`table.balances` 在 `@media (max-width: 30rem)` 把表的各部分改成區塊，欄標題只留給讀屏軟體，與 `.stack` 同一個作法，因為帳戶名是自由文字，旁邊有「已確認」那幾行時，在 320px 它被擠成一兩個字一行；標記上的 `role` 讓它仍是一張表。
- **交易的列**（`.tx`）：一列的格子依序是日期、標題（`<th scope="row">`，就只有標題）、細節（`<td class="tx-sub">`：商家、類別、種類、分期、帳戶與領域／專案的晶片）、狀態、金額。標題與細節排在同一欄，一上一下，但是各自的一格，所以讀屏軟體念列標題時只念標題。標題最多兩行（`title` 有完整的字，完整的內容在交易頁）；每列一個連結，就是標題，聚焦時有 3px 的框。卡片的排法讓整張卡片都是它的點擊範圍，所以卡片裡的標題有底線（沒有滑鼠的連結要有看得出是連結的線索），表裡滑過才有。
- **斷點**：一列都是一個 grid，格子用名字放進去，表頭與列用同一組欄寬，所以對得齊。60rem 以上是表的樣子：四欄（日期 7rem、交易，其餘寬度、標題上細節下，狀態 5.25rem、金額 10.5rem），欄標題看得到（「細節」只給讀屏軟體）。60rem 以下每一列是一張卡片：標題在左、金額在右（金額欄最多佔卡片的 45%），細節在下面，用整張卡片的寬度（長的帳戶名與領域、專案的晶片才排得進同一行），日期與狀態在最下面一行；欄標題只留給讀屏軟體，標記上的 `role` 讓它仍是一張表。篩選的工具列 48rem 以上排成一列，以下帳戶一列、狀態與種類並排；40rem 以下月份的按鈕縮小，讓上個月、月份、下個月排得進一列。
- **中文不一字一行**：標題是自由文字，照中文的方式折行，欄寬與卡片的排法保證它不會窄到一字一行；名稱（商家、類別、帳戶、領域、專案、金額的標籤）用 `word-break: keep-all` 整個留著，一個東西的幾個名字之間（`、` 之後有 `<wbr>`）與東西之間才折行；只有比整個欄還寬的名稱才用 `overflow-wrap: anywhere` 在最後硬折。自由文字不用 `keep-all`：它只剩空白處能折，WebKit 會把「。」擠到行首。
- **可及性**：列標題只有標題；標題的連結被截成兩行的是連結自己，所以聚焦框不會被截掉；列在滑過與聚焦時變色；下拉與按鈕的邊用 `--control-border`；強制色彩模式下藥丸與晶片有框；沒有動畫，沒有 JavaScript。
